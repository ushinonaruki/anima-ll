### 0.3 結論の先取り

1. **出口**（§2）：行動の源の Unit の発火（I1）から、**専用の出力路 `intent`** で、意図 X の Delta を Effector だけへ出す。既存の出力（relay）の振る舞いはそのまま残す。Runtime・Effector は意図を選ばない。意図の発生は Unit の状態を変えない
2. **世界**（§3）：Effector が受けた意図を、明示した**世界の状態**（予約の列）に記録し、t ＋ L − 1 に結果の Receptor へ刺激を出す。今の Pulse の順序では、意図の出来事は感覚の収集より後に配送されるので、**L ≥ 2 でなければならない**（命題 W-1）。結果は Receptor からだけ戻る（AI6）。行動の源の Receptor には刺激を来させない（K1）
3. **完全な複製**（§4）：G-6・PC-4 の比較は、脳の側（Unit の状態・重み・痕跡・届く途中の駆動と Delta・識別子の発行の状態）と世界の側（予約の列・世界の計数。Receptor は予定を持たない：WC-1b）を**すべて**写す。今の `IndividualSnapshot`（Unit と可塑的な接続だけ）では足りない（監査 016）。第一候補の方式は、0012 以来の研究用の道具と同じ**個体と世界の丸ごとの複製**（`copy.deepcopy`）で、介入しない複製が本体と完全に一致することを契約テストにする。標準と決めるのは、その契約テストを通した後（②）【候補】
4. **介入**（§5）：CF-2・FB-1・FB-2・PC-1〜PC-4 を、**接続の状態の口（`ConnectionStatePort`）を包む研究用の部品**と、世界の側の操作だけで行う。Unit の力学・パラメータには触れない。介入は「種類・対象の接続・区間・痕跡の扱い」で宣言し、記録し、「介入なしの包み ≡ 包みなし」を契約テストにする。今の組み立ての口（`build_application`）には接続の状態を差し替える口がないので、**一つ足すか、別の作り方にするかは②の実装の PR で決める**【未決】
5. **ハードコードしない**（§6）：行動の源の発火の条件・意図の頻度・結果の中身・学習の向きを、規則に書かない。C0 のパラメータ（λ・κ・θ・c・α・w_max・τ_a など）は変えない。L は結果を見る前に、独立の理由で決める。沈黙や期待と逆の可塑性が出ても、パラメータを合わせて直さない

## 2. 契約 1：脳由来の行動の意図の出口

### 2.1 今のコードでの事実【既存の事実】

- Unit の出力の部品は 1 つの Unit に 1 つで（`GenericCognitiveUnit` の `output`）、発火のときだけ `on_fire(view)` が呼ばれる。C0 の Unit の出力は relay（`RelayOutput`：新しく届いた内容を CONTENT として転送する）。0012 系の世界では感覚の出来事に中身がないので、C0 では脳の中の Delta は生まれない
- Delta の届け先は、出力路ごとの投射で決まる（`ProjectionRouter.route(source_id, port)`）。出力路の既定は `main`（`DEFAULT_PORT`）。`PulseRuntime` は確定した Delta を、届け先が Effector かどうかで分け、Effector 宛てを Pulse の末尾（伝達・積分・可塑性の更新の後）に配送する
- 発火を駆動として Effector に流す経路は作らない（活動の伝達の仕様 §7。`route_activity` は Effector を除く）
- 研究用の設計図の `effectors` は空（`experiments/0012_passive_world/neuroarchitecture.yaml`）

### 2.2 契約

| ID | 契約 | 契約テスト |
|---|---|---|
| **IC-1** 出どころ | 意図は、源の Unit の出力の部品からだけ生まれる（AI1）。源の発火 1 回につき、ちょうど 1 つの意図の Delta を出す。それ以外の条件（活動の値・時刻・過去の結果）を読まない（I1） | 源の発火の Pulse と、意図の Delta の Pulse が 1 対 1 で一致する。源以外の Unit からは意図が出ない |

## 3. 契約 2：世界からの帰還

### 3.1 命題 W-1（今の Pulse の順序では、L ≥ 2 でなければならない）【命題】

**前提**：`PulseRuntime.run_pulse` の順序【既存の事実】。1. 感覚の出来事の収集（Receptor の `drain(pulse)`）→ 4. Unit を進める（発火と、出力の部品の提案）→ 6. Delta の確定・駆動の積分・可塑性の更新 → 7. Effector への配送。Receptor は、返す出来事にその Pulse の番号を書く（`SensoryPulseMismatch`）。

**主張**：Pulse t の発火から生まれた意図が、世界に届くのは Pulse t の 7 で、Pulse t の 1（感覚の収集）はもう終わっている。したがって結果の刺激が成立しうる最も早い Pulse は t ＋ 1 で、L − 1 ≥ 1、つまり L ≥ 2。∎

- L ＝ 2 では、世界は Pulse t の配送のときに、Pulse t ＋ 1 の結果を自分の予約の列に足す（正本は世界だけ：WC-1b）。まだ drain していない Pulse にだけ予約でき、過ぎた Pulse への予約は止める（0012 の `ScheduledReceptor.inject` と同じ検査を、世界の予約の列に置く）
- L の値を、期待する結果に合わせて選ばない（§6）

### 3.1b 命題 W-2（AS1 の最小の構成では、結果の予約は同じ Pulse に重ならない）【命題】

**前提**：源は 1 つで、Unit は 1 Pulse に高々 1 回発火する（`docs/core-structural-reassessment.md` §1.2）。I1 なので、意図は 1 Pulse に高々 1 つ。L は固定。結果の Receptor に、行動に依らない刺激を置かない。

**主張**：結果の Receptor に Pulse u に成立する予約は、高々 1 つ（Pulse u − L ＋ 1 の意図からのものだけ）。∎

- したがって、この構成では「1 予約に 1 出来事」と「まとめる」の規則が同じ感覚の列を与え、G-6 の e の取り消しは、Pulse t ＋ 1 の結果の Receptor の出来事を 1 つ確実に消す
- 行動に依らない刺激を結果の Receptor に置く、L を可変にする、などで前提が崩れるときは、WC-1c の多重度の規則が効く。**G-6 の e は予約の識別子の単位で定め、その取り消しが感覚の列をどう変えるかは、多重度の規則から決まる**

### 3.2 契約

| ID | 契約 | 契約テスト |
|---|---|---|
| **WC-1** 世界の状態を明示する | 世界の規則は一つの研究用の部品（世界）にまとめ、状態をすべて明示する：結果の予約の列（成立の Pulse と Receptor）、行動に依らない刺激の予定、受けた意図の記録、計数。Effector は受けた意図を世界に渡すだけ | 世界の状態を書き出せ、複製で一致する（§4） |
| **WC-1b** 予約の正本は一つ | 結果の刺激の予約の**正本は世界の予約の列だけ**に置く。結果の Receptor（と、置くなら行動に依らない刺激の Receptor）は自分の予定を持たず、`drain(pulse)` のときに、世界にその Pulse に成立する出来事を問い合わせて返す（最後に drain した Pulse だけを持つ）。予約を Receptor の予定へ写す二重の持ち方をしない | Receptor が返した出来事の列と、世界の予約の列の、その Pulse の分が一致する |
| **WC-1c** 予約の識別と多重度 | 予約は一つずつ識別子（出どころの意図の識別子か通し番号、種類〔結果・行動に依らない刺激〕、Receptor、成立の Pulse）を持つ多重集合として持つ。Pulse ごとの集合（0012 の `ScheduledReceptor` の形）では持たない。同じ Receptor・同じ Pulse に複数の予約が重なったとき、予約ごとに感覚の出来事を一つずつ成立させるか、一つにまとめるかを、世界の規則として事前に書く【未決（③）。AS1 の第一候補は「1 予約に 1 出来事」】。取り消しは識別子で一つの予約だけに作用する。**予約の取り消しと、感覚の出来事の消失は同じではない**（まとめる規則では、ほかの予約が残れば出来事は残る） | 重なった予約から一つを取り消すと、成立する出来事の数が規則どおりに変わる（まとめる規則なら、ほかの予約が残る限り出来事は残る、と記録する） |
| **WC-2** 規則は固定 | 「意図 X が Pulse t に来たら、結果の Receptor に Pulse t ＋ L − 1 の刺激を予約する」だけ。結果の中身は空（中身のない感覚の出来事）。意図がなければ何もしない。規則は実験の前に固定する | 予約の列が、意図の記録から規則どおりに決まる |
| **WC-3** 戻り道は Receptor だけ | 世界は Unit の状態・接続・駆動に触れない。成功・失敗の信号を返さない（AI3・AI6） | 世界の部品が脳の部品への参照を持たない（構成の監査）。脳への入力は Receptor の出来事だけ |

## 4. 契約 3：途中の状態の完全な複製（監査 016・018）

### 4.1 複製しなければならない状態 Σ

G-6 の比較（三段の比較 §3.2）・PC-4 の移植（§3.3.4）・CF-2 などの介入の比較は、分岐の時点の状態 Σ を、次の**すべて**について二つの系で同じにする。

|---|---|---|
| 脳 | Unit の状態（activity・順応・不応の残り） | 各 Unit（`export_state`） |
| 脳 | 可塑的な接続の重み・送り手と受け手の痕跡 | `ConnectionStore`（`export_state`） |
| 脳 | 届く途中の駆動（前の Pulse に成立し、次の Pulse に届く `Drive`） | `PulseRuntime._state`（`BrainState.drives`） |
| 脳 | 確定済みの Delta（TTL の残り） | `BrainState.deltas` |
| 脳 | 識別子の発行の状態 | `IdentifierIssuer` |
| 脳 | Pulse の番号・時計 | `RuntimeLifecycle`・`FixedStepClock` |
| 脳 | 計算の依頼の列・Worker | `KernelTaskCoordinator`（AS1 では使わない。空であることを確かめる） |

| 世界 | Effector の状態 | 各 Effector |

- **今の `IndividualSnapshot` では足りない**【既存の事実】：`RuntimeLifecycle.save_snapshot` が保存するのは、Unit の状態と可塑的な接続の状態だけで、届く途中の駆動・Delta・識別子の発行・世界の状態を含まない（監査 016）。`IndividualSnapshot` は個体の保存形式として設計されたもので（「実行基盤の状態は含めない」）、それ自体は誤りではない

### 4.2 複製の方式【候補】

| 方式 | 中身 | 利点 | 限界 |

| **M1 丸ごとの複製（第一候補）** | 個体（`Application`）と世界の部品を、まとめて `copy.deepcopy` する。来歴のログだけ新しい空のものに替える | 0012 以来の研究用の道具と同じ方式（`experiments/0012_passive_world/world.py` の `clone`）。Σ のすべてが一つの物の網に入っていれば、漏れなく写る。Core を変えない | 世界の部品が個体の外にあれば、同じ deepcopy の呼び出しで一緒に写す必要がある（別々に写すと、Effector から世界への参照が切れる）。非同期の処理が残っていると写らない |

- 世界の側の介入（G-6 の系 N で e だけを除く）は、**Pulse t の処理（7 の配送で e が予約された後）を終えて、Pulse t ＋ 1 を始める前**に、個体を複製し、**複製の世界の予約の列（正本：WC-1b）から e だけを除く**。結果の Receptor は予定を持たないので、ほかに消す場所はない。研究用の道具は、`run(max_pulses=t)` で Pulse t まで進めてから複製する（Pulse のあいだで止まる）

### 5.2 実装の形【候補】

- **接続の状態の口を包む部品**：`ConnectionStatePort` の 3 つの操作（`weights`・`apply_activity`・`export_state`）を持ち、中の `ConnectionStore` に渡す研究用の部品
  - FB-1：対象の接続について、`weights()` が伝達に返す値だけを 0 にする。中の重みは規則どおり更新され続ける（G-7：「重み 0 にする」とは違う）
  - **FB-1 の契約は「活動への寄与が 0」**とする。今の `_transmit()` は、伝達の重みが 0 でも `Drive(weight=0)` を作る【既存の事実】。Unit は駆動の重みの和だけを読む（`GenericCognitiveUnit.tick`）ので、重み 0 の駆動は活動に寄与しない。「駆動そのものを作らない」形は、Runtime の伝達の変更になるので採らない。記録の上では重み 0 の駆動が残る。**重み 0 の駆動と、駆動がないことを同じとみなさない**：記録（VIEW の駆動の一覧・`BrainState.drives`）の比較では、FB-1 の系に重み 0 の駆動があることを差として書き、活動の一致（CT-I2）とは分ける
  - FREEZE：`apply_activity` の後に、対象の接続の重みを区間の始まりの値に戻す（痕跡は宣言どおり）
  - TRANSPLANT：区間の始まりに、公開の `import_state` で、宣言した重みを置き換える（0030 で使った公開の口と同じ）
- **組み立ての口**【未決】：今の `build_application` は `ConnectionStore(manifest)` を中で作り、差し替える口がない。次のどれにするかは②の実装の PR で決める
  - (a) `build_application` に、接続の状態を包む部品を受け取る省略可能な引数を一つ足す（組み立ての口の変更。Unit の力学・可塑性の規則・パラメータは変えない）
  - (b) 研究用の道具の側で、同じ部品から `PulseRuntime` を組み立てる
  - (c) 可塑性を止める比較（PC-1・PC-3）は、0030 と同じく可塑性のない設計図の変種と公開の `import_state` で作る（区間の途中での切り替えはできない）
- OPEN-LOOP：世界の部品の代わりに、記録した感覚の列を Pulse の番号で持つ Receptor（0012 の `ScheduledReceptor` と同じ型）を使う。出口の意図は記録するが、結果を持たない

## 6. ハードコードしない・合わせて直さない【契約】

- **行動の源の発火の条件を書かない**：意図は「源が発火したら」だけで、活動の値・時刻・直前の刺激・過去の結果を条件にしない（I1）。発火の頻度を目標に合わせる部品を足さない
- **結果の中身を書かない**：結果の刺激は中身のない感覚の出来事で、「よい」「わるい」の区別を持たない（AI6）
- **学習の向きを書かない**：帰還の重みが強まる・弱まる、を規則に書かない。期待する向きも事前に決めない（三段の比較 G-10・監査 013・017。台帳 017 の判定では、K1 と C0 の条件のもとで、孤立した 1 周の到達しうる k は 5 以上で、w0 では正味が負になる。これも全発火列の一般の結論ではない）
- **C0 のパラメータを変えない**：Unit の力学（λ・θ・c とそのばらつき・順応・不応）、可塑性（κ・a・w_max・w0）、Receptor の入力の重み 1.0 は、研究用の設計図の値のまま
- **L は結果の前に、独立の理由で決める**（候補 L ＝ 2：C0 の世界の時間差に合わせて比較可能性を保つ）。複数の L を試して都合のよいものを選ばない
- **沈黙は直さない**：源が沈黙して閉ループが閉じない個体が出ても、パラメータ・割り当てを変えて回避しない。その個体の数と理由を記録する（N-3・N-4 §3.6）。割り当てを結果を見て選び直さない
- **期待と逆の可塑性**：帰還が弱まる、B ＝ 0 が多い、などは、それ自体を失敗とせず、モデルの性質として記録する
