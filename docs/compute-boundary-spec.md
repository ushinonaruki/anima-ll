# 計算資源境界 仕様 v0.3

> 作成：2026-10-07。Status：**仕様（ChatGPT レビュー 2 回分を反映）。実装はまだしない**
> 対象：恣意性監査 §3.1（計算資源の取り合い：容量・負けたら消える・計算中なら消える・claim ＝ activity）
> 進め方：症状（u2 の取り残し）を直す設計から入らない。先に、各層が何を決め、何を保証するかを決める
>
> v0.3 での変更：
> - **実行の順番は「認知的な意味を持たない工学的な方針」と位置づけ、FIFO はその参照実装に格下げ**（「FIFO を AnIma-ll の原理として採用する」のではない）
> - 「GPU でどの仕事から計算するか（実行のスケジューリング）」と「どの認知活動が表に出るか（認知的な競合）」を明確に分けた（§5）
> - 同じ Pulse の中の順番は、単調に増える通し番号（intent_seq）だけで決める。round-robin は使わない
> - 同じ Unit の実行は同時に 1 件まで（1 in-flight）。意図は何件でも受け付ける
> - 列のあふれは、新しく来た意図を受け付けない（tail-drop）。古いものを捨てない。Kernel の失敗とは別の状態として記録する。上限は計算資源の種類ごと
> - 不変条件の言い方を「Worker 数や Kernel の速さだけを理由に、成立済みの ComputeIntent の存在・生成時刻・入力内容を遡って変えない」に直し、テスト方法を契約テストに変えた
> - §8 の「活動が増えるのは副作用ではない」を、「silent drop をやめた直接の影響として記録する。ただし認知特性とは解釈しない」に直した
>
> v0.2 での変更：不変条件を「遅れだけが変わる」から弱めて正確にした。claim の強さを廃止候補に。列のあふれを Runtime の劣化として扱う

## 1. 境界

```text
【Neuroarchitecture / Unit】ここまでが認知
  受容野（ReceptiveView）
    ↓
  局所の力学
    ↓
  発火などの認知の出来事
    ↓
  ComputeIntent（計算の意図）を生成
──────────────────────────────────────
【Runtime / 実行基盤】
    ↓
  検証（権限・契約）→ intent_seq を付ける
    ↓
  実行待ちの列（計算資源の種類ごと）
    ↓
  空いた Worker へ渡す
    ↓
【Compute Kernel】
  計算 → KernelResult
    ↓
【Runtime】
  意図を出した Unit へ返す（Shared Brain State に入るのは Pulse の境界から）
```

**ComputeIntent** は「この時点で、この材料を使って、高価な計算をしたい」という、**すでに成立した認知の出来事** である。列が持っているのは心理状態ではなく、すでに発生した仕事である。

## 2. 各層の責務

### 2.1 Unit（Neuroarchitecture）

- いつ発火するかを決める（力学）。発火したとき、出力の部品が高価な計算を必要とするなら ComputeIntent を出す。**ここで認知の判断は終わる**
- 発火したこと（activity を 0 に戻す、順応を積む）は、計算がいつ実行されるかに関係しない（今もそうなっている）
- Unit は、計算資源の空き・Worker の数・列の長さを知らない。結果が返ってきたときに受け取るだけ

### 2.2 ComputeIntent（不変の仕事）

生成した時点で次を **凍結** する。後から変えない。

| 項目 | 中身 |
|---|---|
| intent_id | 一意の ID |
| unit_id・created_pulse | 生成した Unit・Pulse |
| resource_class | どの計算資源を使うか |
| KernelTaskDraft | Kernel に渡す材料と IO テンプレート（**生成した Pulse の受容野から作る**） |
| input_delta_ids | 材料にした Delta |
| origin_snapshot_id | 材料を見たスナップショット |

実行時に BrainState を引き直さない。材料の Delta がその後に保持期間を過ぎて消えても関係ない（「Pulse 100 で A を見て考えようとした」意図は、Pulse 110 に実行されても A を材料に計算する）。

L2-2 では、実行される Pulse の受容野から中身を作り直していた。それだと、Worker が混んでいたせいで「何を考えたかったか」まで変わる。実行基盤の列ではそれをしない。

### 2.3 Runtime（実行基盤）

**保証すること**

1. **合法な意図は受理し、実行待ちとして保持する。容量不足や計算中（busy）を理由に黙って消さない。** 容量が足りないのは「実行できない」ではなく「まだ実行されていない」
2. **計算中の Unit の新しい意図も受理する。** ただし **同じ Unit の実行は同時に 1 件まで（1 in-flight）**。前の計算が終わってから次を Worker に渡す。複数の Worker は、異なる Unit の間の並列に使う
3. **実行の順番は §4 の工学的な方針に従う。** 参照実装は、Runtime が受理した順に付ける単調増加の `intent_seq` による FIFO
4. 結果は、意図を出した Unit に、意図を出した順に返る（2 の 1 in-flight により自然に保たれる）
5. どの意図も、最後には次のどれかとしてログに残る

```text
intent_created → intent_admitted → intent_started → intent_completed
                                                  └→ intent_kernel_error
intent_created → intent_rejected_overflow（§3.3）
```

**しないこと**：意図に優先度や価値をつけて選ぶこと。それは認知的な競合であり、扱うなら脳の設計図の側で扱う（§5）

### 2.4 Compute Kernel

- `KernelTaskDraft` だけを受け取り、「入力 → 高価な変換 → 結果」だけを行う
- **知らないもの**：人格、Birth State、Unit の activity・順応、ほかの Unit の状態、列、Worker の数、なぜその意図が生じたか
- 「この要求は重要だから実行すべきか」を Kernel に判断させない。それは意図が生成された時点で決着している

### 2.5 Environment（実行環境）

- 物理的な実行能力だけを持つ：Kernel の実装、モデル、Worker の数（今の `capacity`）、**計算資源の種類ごとの列の上限**
- AnIma-ll にとっては「身体の性能」に近い

## 3. 不変条件と、その例外

### 3.1 不変条件

> **Worker の数や Kernel の速さだけを理由として、すでに成立した ComputeIntent の存在・生成時刻・入力内容を遡って変更しない。**

| 変わってよいもの | 変わってはいけないもの |
|---|---|
| 実時間での待ち時間 | その意図が発生したか |
| 結果が返る Pulse | intent_id・created_pulse |
| 列の長さ | 凍結した下書き・input_delta_ids・origin_snapshot_id |
| CPU・GPU の使用量 | 容量不足を理由に意図が消えるかどうか（消えない） |

ただし **結果が返るタイミングが変われば、その後の Unit の発火・次の意図・発話は変わりうる**。列があふれるかどうかも変わりうる。要求するのは「Worker の数を変えても同じ人生になる」ことではない。

### 3.2 確かめ方（実装のときのテスト）

- **契約テスト**：同じ Unit の出力（UnitStepResult）を Runtime に渡し、空き Worker が 0・1・4 のどの場合でも、作られる ComputeIntent（intent_id・created_pulse・snapshot・input_delta_ids・draft）が同じであること。違うのは queued・started・completed の時刻だけ
- **結合テスト**：結果を一定期間返さない FakeKernel で、Worker 1 と 4 を数十 Pulse 走らせる。**結果がまだ 1 件も返っていない区間** では、ComputeIntent の列が完全に一致すること
- 結果が一度返った後は、Worker の数 → 結果が返るタイミング → 後続の Unit の状態、と変わるので、run 全体の一致は要求しない

### 3.3 列があふれたとき（例外）

意図が出る速さが計算の速さを上回り続けると、列は伸び続ける（0006 では計算の要求が約 4 倍になった）。

- 上限は計算資源の種類ごとに Environment で決める
- 上限に達したら、**新しく来た意図を受け付けない（tail-drop）**。すでに受理した意図は捨てない
  - 古いものから捨てる方式（head-drop）にしないのは、「古い考えは新しい考えより価値が低い」という認知的な価値判断が実行基盤に入るため
  - 受け付けなかった意図も **認知の出来事としては存在した** ものとして、`intent_rejected_overflow` で記録する。無かったことにはしない
  - Kernel の失敗（`intent_kernel_error`）とは原因が違うので、別の状態にする
- あふれが起きた run は **Runtime の劣化（異常）** として扱い、その間の結果を AnIma-ll の認知として解釈しない。tail-drop を選んだことが結論に影響しないのは、この扱いがあるため
- **あふれは、Kernel が Unit の生み出す認知の出来事の量に対して遅すぎる、という性能不足の計測結果として正面から扱う。** あふれを減らすための機構を認知の側に足さない（恣意性監査 §2.2 の問い 4）

## 4. 実行の順番は「工学的な方針」であって、原理ではない

**FIFO も、1 in-flight も、tail-drop も、Engineering choice である。** どれも「脳として正しいから」選んだのではない。選んだ理由は、**認知的な意味をなるべく持たない** ことである。

- 実行の順番：**認知的な意味を持たない Engineering policy。現時点では FIFO（intent_seq 順）を参照実装とする**
- FIFO が使う情報は「いつ受理されたか」だけで、意図の中身にも Unit の状態にも頼らない
- 意図を捨てないので、順番の決め方で変わるのは **結果が返るまでの待ち時間だけ**。「何を考えようとしたか」は変わらない（§3.1）

**判定の基準**：実行基盤の規則を別の規則に入れ替えたとき、§3.1 の「変わってはいけないもの」が変わるなら、その規則は認知に漏れている。

| 規則 | 漏れるか | 根拠 |
|---|---|---|
| 強さ（activity）順で、負けたら捨てる（今の実装） | **漏れる** | どの意図が存在し続けるかを決めている |
| FIFO（参照実装） | 漏れない | 待ち時間だけが変わる |
| 1 in-flight | 漏れない | 待ち時間だけが変わる。代わりに結果を後で並べ替える仕組みも作れるが、仕組みが増える |
| tail-drop | 正常系では関係しない | 劣化した run は解釈しない |

参照実装なので、同じ基準を満たす別の方針に入れ替えてよい。そのときは台帳に記録する。

## 5. 実行のスケジューリングと認知的な競合を分ける

| | A. 実行のスケジューリング | B. 認知的な競合 |
|---|---|---|
| 問い | GPU でどの仕事から計算するか | どの認知活動が表に出るか |
| 層 | Runtime・Environment | Neuroarchitecture |
| 性格 | 認知ではない | 認知の原理 |
| 方針 | 単純な工学ルール（§4） | 独立した原理として比較・検討する |
| Worker の数 | 依存してよい | 依存してはいけない（Worker 1 でも 8 でも同じ原理） |

「強いものが勝ちやすいが、弱いものにも順番が回る」という **強さ順とランダムの中間** の仕組み（softmax・重みつきくじ引き・確率的な閾値・側方抑制など）は存在する。しかし、それを **A（LLM の実行の列）に入れない**。入れると、また GPU の順番決めを認知のモデルとして使うことになり、L2-2 の混同に戻る。

扱うなら **B の側** で、次の順に検討する。

1. 今の Unit の力学（activity → 閾値 → 発火 → 順応）だけで、すでに「強さ順と偶然性の中間」をどこまで担っているかを先に監査する。順応（L2-1）は、よく発火した Unit ほど発火しにくくし、その間に他の Unit が発火できるようにする、**決定論的な** 中間の仕組みになっている
2. 今は run 中が決定論的（同じ状態なら必ず同じ結果）である。生物の神経活動の確率性・ノイズを、AnIma-ll の粗い模型にどう位置づけるかは、**独立した認知の原理の問い** として監査台帳に置く（§3.9）
3. 「u2 を救いたいからランダム性を足す」「単調さを崩したいから温度を足す」という理由では入れない（恣意性監査 §2.2）。温度などの値を適当に決めるのも、値の恣意性になる

その後、B に認知的な優先度ができたときに、それを A の順番のヒントに写すかを改めて決める。

## 6. この仕様で扱わないこと

- **認知的な競合（注意・顕著性・緊急度・確率的な発火など）**：§5 の B。この仕様の外
- **不応期**（監査 §3.2）：もともと「同じ Unit が計算資源を連続で占有しない」ためだった。この仕様でその役目は実行基盤（1 in-flight と列）に移る。不応期そのものの扱いは次の監査項目
- **Delta の保持期間・最新 8 件**（監査 §3.4・3.5）：時間と記憶の設計と一緒に

## 7. 個別の位置づけと、今の実装とのずれ

| 項目 | 結論 | 今の実装とのずれ |
|---|---|---|
| Resource Scheduler・容量 | **Engineering infrastructure**。認知的な競合を表していない | — |
| `rejected_capacity`・`dropped_busy` | 正常系としては廃止。容量不足・計算中は「まだ実行されていない」 | 変更が必要（今は消える） |
| `ComputeClaim.strength`（＝ min(1, activity)） | **廃止候補**。実行の順番には使わない。activity → claim → GPU の優先度、という接続を外す。activity そのものは Unit に残る | 変更が必要 |
| 実行の順番 | 工学的な方針。参照実装は intent_seq の FIFO | 変更が必要（今は claim の強さ順） |
| 同点のとき毎 Pulse 順番を回す（round-robin） | **廃止**。意図を捨てないので不要。L0 の症状への対処を理由なく引き継がない | 変更が必要 |
| 同じ Unit の実行は 1 件まで | 「busy 中の新しい要求を捨てる」から「1 in-flight、新しい意図は保存して後で渡す」に意味を変える | 変更が必要 |
| 列の上限・あふれ | 計算資源の種類ごとの上限、tail-drop、`intent_rejected_overflow`、劣化として記録 | 追加が必要 |
| 1 Unit 1 Pulse 1 件まで | Runtime の契約上の暫定的な足場（Integration scaffold）として残す。違反は今のとおり `extra_compute_request`。**「脳も 1 Pulse に 1 つしか考えを出せない」とは解釈しない**。後で別に監査する | なし |
| 下書きは生成した Pulse の受容野から（凍結） | 採用 | なし |
| 発火の結果（activity・順応）は実行と無関係 | 採用 | なし |
| Kernel は下書きだけを受け取る | 採用 | なし |

## 8. 予想される影響（先に書いておく）

- 実装を変えると、`minimal-v1` の上での振る舞いは変わる。これまで消えていた u1・u2 の計算が実行され、u1 ↔ u2 の相互結合が働いて活動が増える見込みが高い（0006 と同じ方向）
- **活動の増加は、silent drop をやめた直接の影響として記録する。** ただし、その増加量や持続性は、動作テスト用の配線・文章をやり取りする内部表現（監査 §3.6・3.8）などの足場にも依存するため、**AnIma-ll の認知特性とは解釈せず、増加を打ち消すための認知機構も追加しない**
- これまでの実験（0002〜0005）は「要求が消える実行基盤」の上で得たものとして、前提つきで読む。変更後に基準をとり直すかどうかは、実装のときに事前登録で決める
