# 計算資源境界 仕様 v0.2

> 作成：2026-10-07。Status：**仕様（ChatGPT レビュー反映済み）。実装はまだしない**
> 対象：恣意性監査 §3.1（計算資源の取り合い：容量・負けたら消える・計算中なら消える・claim ＝ activity）
> 進め方：症状（u2 の取り残し）を直す設計から入らない。先に、各層が何を決め、何を保証するかを決める
>
> v0.1 からの変更：不変条件を「遅れだけが変わる」から「資源不足だけを理由に認知の出来事を消さない・変えない」に弱めて正確にした。同じ Pulse の中の順番を Unit ID 順に。claim の強さを廃止候補に。列のあふれを Runtime の劣化（異常）として扱う。1 Pulse 1 件の位置づけ、Kernel が知らないものを追加

## 1. 境界

```text
【Neuroarchitecture / Unit】ここまでが認知
  受容野（ReceptiveView）
    ↓
  局所の力学
    ↓
  発火などの認知の出来事
    ↓
  ComputeIntent（計算の意図）を生成
──────────────────────────────────────
【Runtime / 実行基盤】
    ↓
  検証（権限・契約）
    ↓
  実行待ちの列
    ↓
  空いた Worker へ渡す
    ↓
【Compute Kernel】
  計算 → KernelResult
    ↓
【Runtime】
  意図を出した Unit へ返す（Shared Brain State に入るのは Pulse の境界から）
```

**ComputeIntent** は「この時点で、この材料を使って、高価な計算をしたい」という、**すでに成立した認知の出来事** である。列が持っているのは心理状態ではなく、すでに発生した仕事である。

## 2. 各層の責務

### 2.1 Unit（Neuroarchitecture）

- いつ発火するかを決める（力学）。発火したとき、出力の部品が高価な計算を必要とするなら ComputeIntent を出す。**ここで認知の判断は終わる**
- 発火したこと（activity を 0 に戻す、順応を積む）は、計算がいつ実行されるかに関係しない（今もそうなっている）
- Unit は、計算資源の空き・Worker の数・列の長さを知らない。結果が返ってきたときに受け取るだけ

### 2.2 ComputeIntent（不変の仕事）

生成した時点で次を **凍結** する。後から変えない。

| 項目 | 中身 |
|---|---|
| 生成した Unit・Pulse | — |
| resource_class | どの計算資源を使うか |
| KernelTaskDraft | Kernel に渡す材料と IO テンプレート（**生成した Pulse の受容野から作る**） |
| input_delta_ids | 材料にした Delta |
| origin_snapshot_id | 材料を見たスナップショット |

L2-2 では、実行される Pulse の受容野から中身を作り直していた。それだと、Worker が混んでいたせいで「何を考えたかったか」まで変わる。実行基盤の列ではそれをしない。

### 2.3 Runtime（実行基盤）

**保証すること**

1. **合法な意図は受理し、実行待ちとして保持する。容量不足や計算中（busy）を理由に黙って消さない。** 「容量の取り合いに負けた」という正常系そのものをなくす。容量が足りないのは「実行できない」ではなく「まだ実行されていない」
2. **計算中の Unit の新しい意図も受理する。** 同じ Unit の意図が「実行中 1 本 ＋ 待ち数本」になってよい。Kernel が遅いほど意図が消える、ということが起きないように
3. **実行の順番は決定論的な先入れ先出し（FIFO）**：生成した Pulse → Unit ID → 同じ Unit の中の生成順。内容にも Unit の状態にもよらない
4. 結果は、意図を出した Unit に、意図を出した順に返す
5. どの意図も、最後には「計算が終わった」「Kernel が失敗した」「Runtime が劣化して捨てた（§3.2）」のどれかとしてログに残る

**しないこと**：意図に優先度や価値をつけて選ぶこと。それは認知の競合であり、必要になったら脳の設計図の側に独立した原理として作る（§4）

### 2.4 Compute Kernel

- `KernelTaskDraft` だけを受け取り、「入力 → 高価な変換 → 結果」だけを行う
- **知らないもの**：人格、Birth State、Unit の activity・順応、ほかの Unit の状態、列、Worker の数、なぜその意図が生じたか
- 「この要求は重要だから実行すべきか」を Kernel に判断させない。それは意図が生成された時点で決着している

### 2.5 Environment（実行環境）

- 物理的な実行能力だけを持つ：Kernel の実装、モデル、Worker の数（今の `capacity`）、列の上限
- AnIma-ll にとっては「身体の性能」に近い

## 3. 不変条件と、その例外

### 3.1 Worker の数を変えたとき

| 変わってよいもの | 変わってはいけないもの |
|---|---|
| 実時間での待ち時間 | その意図が発生したか |
| 結果が返る Pulse | 意図の材料（凍結した下書き・入力の Delta） |
| 列の長さ | 意図の origin snapshot |
| CPU・GPU の使用量 | 容量不足を理由に意図が消えるかどうか（消えない） |

ただし **結果が返るタイミングが変われば、その後の Unit の発火・次の意図・発話は変わりうる**。これは避けられない。要求する不変性は「Worker の数を変えても同じ人生になる」ではなく、次のとおり。

> **実行資源の不足だけを理由として、すでに成立した認知の出来事を抹消・改変しない。**

確かめ方（実装のときのテスト）：同じ入力・同じ個体で Worker 1 と 4 を回し、**最初の計算の結果が Unit に戻る Pulse より前** に生成された意図の列（Unit・Pulse・材料）が完全に一致すること。

### 3.2 列があふれたとき（例外）

意図が出る速さが計算の速さを上回り続けると、列は伸び続ける（0006 では計算の要求が約 4 倍になった）。

- 列の上限は Environment の設定。超えたら **Runtime の劣化（異常）** として明示的に記録する（そのとき捨てた意図も記録する）。正常系ではない
- 劣化した実行の結果は、AnIma-ll の認知として解釈しない
- **あふれは、Kernel が Unit の生み出す認知の出来事の量に対して遅すぎる、という性能不足の計測結果として正面から扱う。** 遅いので認知の出来事を無かったことにする、という設計にはしない。あふれを減らすための機構を認知の側に足さない（恣意性監査 §2.2 の問い 4）

## 4. この仕様で扱わないこと

- **認知的な競合（注意・顕著性・緊急度など）**：多数の表象の中から一部だけが処理に上がる仕組みを入れるなら、Worker の数とは独立に、脳の設計図の側に独立した原理として作る。その後で、それを実行の順番のヒントに写すかを改めて決める
- **不応期**（監査 §3.2）：もともと「同じ Unit が計算資源を連続で占有しない」ためだった。この仕様でその役目は実行基盤から外れる。不応期そのものの扱いは次の監査項目
- **Delta の保持期間・最新 8 件**（監査 §3.4・3.5）：時間と記憶の設計と一緒に

## 5. 個別の位置づけ

| 項目 | 結論 |
|---|---|
| Resource Scheduler・容量 | **Engineering infrastructure**。認知的な競合を表していない |
| `rejected_capacity`・`dropped_busy` | 正常系としては廃止。容量不足・計算中は「まだ実行されていない」 |
| `ComputeClaim.strength`（＝ min(1, activity)） | **廃止候補**。実行の順番には使わない。activity が高いほど GPU の列で優先する、という結合に独立した根拠がない。将来、認知的な優先度を独立した原理として入れたときに、改めて写すかを決める |
| 1 Unit 1 Pulse 1 件まで | Runtime の契約上の暫定的な足場（Integration scaffold）として残してよい。違反は今のとおり `extra_compute_request` として記録する。**「脳も 1 Pulse に 1 つしか考えを出せない」とは解釈しない**。後で別に監査する |
| 同点のとき毎 Pulse 順番を回す | 不要になる（意図を捨てないので、同じ Pulse の中の順番は待ち時間を数 Pulse 変えるだけ）。Unit ID 順で決定論的に並べる |

## 6. 今の実装とのずれ（実装は別途）

| 今の実装 | 仕様 | ずれ |
|---|---|---|
| 容量の取り合いに負けた要求は消える | 列に並ぶ | 変更が必要 |
| 計算中の Unit の新しい要求は消える | 列に並ぶ | 変更が必要 |
| 実行の順番は claim の強さ（同点は回す） | FIFO（Pulse → Unit ID → 生成順） | 変更が必要 |
| 列の上限・あふれの扱いはない | Environment の上限と Runtime の劣化の記録 | 追加が必要 |
| 下書きは発火した Pulse の受容野から | 同じ（凍結） | なし |
| 発火の結果（activity・順応）は実行と無関係 | 同じ | なし |
| Kernel は下書きだけを受け取る | 同じ | なし |

## 7. 予想される影響（先に書いておく）

- 実装を変えると、`minimal-v1` の上での振る舞いは変わる。これまで消えていた u1・u2 の計算が実行され、u1 ↔ u2 の相互結合が働いて活動が増える見込みが高い（0006 と同じ方向）
- **それはこの仕様の副作用ではなく、動作テスト用の配線と、文章をやり取りする内部表現（監査 §3.6・3.8）の性質** として記録する。活動の増加を打ち消す機構は足さない
- これまでの実験（0002〜0005）は「要求が消える実行基盤」の上で得たものとして、前提つきで読む。変更後に基準をとり直すかどうかは、実装のときに事前登録で決める
