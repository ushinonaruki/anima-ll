# 認知と計算資源の境界 仕様案 v0.1

> 作成：2026-10-07。Status：叩き台（ChatGPT のレビューと t-k さんの判断待ち）。**実装はしない**
> 対象：恣意性監査 v0.3 §3.1（計算資源の取り合い：容量・負けたら消える・計算中なら消える・claim ＝ activity）
> 進め方：症状（u2 の取り残し）を直す設計から入らない。**先に、各層が何を決め、何を保証するかを決める**。そのうえで、今の実装がその仕様からどれだけずれているかを書く

---

## 1. 問い

1. Unit は何を決めるのか
2. Compute Kernel は何を代わりにやるのか
3. Runtime は何を保証するだけなのか
4. Environment は何を与えるのか
5. Environment の Worker の数が変わっても、AnIma-ll の認知として変わらないべきものは何か

## 2. 各層の責務（案）

### 2.1 Unit（Neuroarchitecture）

- **決めること**：いつ発火するか（力学）。発火したとき、その出力の部品が高価な計算を必要とするなら、**「この材料について計算を使いたい」という意図（ComputeIntent）** を出す
- 意図は、発火した Pulse の受容野から作る（何を材料にするかは、そのときに決まっている）。意図を出した時点で、**認知の判断は終わり**
- 発火したこと（activity を 0 に戻す、順応を積む）は、計算がいつ実行されるか・されるかどうかに **関係しない**（今もそうなっている）
- Unit は、計算資源が空いているか、何本動いているかを知らない。計算の結果が返ってきたときに受け取るだけ

### 2.2 Compute Kernel

- 意図に入っている材料と IO テンプレートから、計算をして結果を返す。それ以外は何もしない
- 本人ではない（凍結 5 点の 5）。交換しても、遅くなっても、AnIma-ll の「何を考えようとしたか」は変わらない

### 2.3 Runtime（実行基盤）

**保証すること**：

1. **出された意図は、計算資源の都合だけで黙って消えない。** どの意図も、最後には「計算が終わった」「Kernel が失敗した」「実行環境の限界を超えて捨てた（§3.3）」のどれかとしてログに残る
2. **実行の順番は、内容にも Unit の状態にもよらない。** 実行基盤は OS の実行待ちの列と同じで、AnIma-ll の心理状態ではない（§3.1 で決める）
3. 結果は、意図を出した Unit に返す。結果が Shared Brain State に入るのは、これまでどおり Pulse の境界から

**しないこと**：意図に優先度や価値をつけて選ぶこと（それは認知の競合であり、もし入れるなら脳の設計図の側に明示的に作る：§4）

### 2.4 Environment（実行環境）

- 計算資源の量（Worker の数）と、Kernel の速さを与える。AnIma-ll にとっては「身体の性能」に近い
- これが変わって変わるのは、**計算が終わるまでの遅れ** だけであるべき

## 3. 決めること（論点と案）

### 3.1 実行の順番：claim をどう扱うか

| 案 | 中身 | 長所 | 短所 |
|---|---|---|---|
| **A. 到着順**（同じ Pulse の中は順番を回す） | 意図を出した Pulse の順。同じ Pulse の中は、毎 Pulse 回す（今の同点の扱いと同じ考え方） | 内容にも状態にもよらない。実行基盤として素直 | claim の強さは使わなくなる |
| B. claim の強さの順 | 同じ Pulse の中は activity が高い順 | 今の実装に近い | 認知の activity が実行の順番を決める。§2.3 の 2 に反する |

**A を推す。** claim の強さ（`ComputeClaim.strength`）は、実行の順番には使わない。値はログに残す（観察用）。

### 3.2 計算中の Unit がまた発火したら

| 案 | 中身 |
|---|---|
| **A. 新しい意図も列に並べる** | 1 Unit が同時に複数の計算を持てる。結果は出した順に返る |
| B. 前の計算が終わるまで並べない（今の「1 Unit 1 タスク」） | 計算の遅さが、Unit の「考えようとしたか」を消す。§2.3 の 1 に反する |

**A を推す。** 「1 Unit 1 Pulse 1 件まで」（1 回の発火で意図は 1 本）は契約として残す。

### 3.3 列があふれたら（実行環境の限界）

意図が出る速さが計算の速さを上回り続けると、列は伸び続ける（0006 では計算の要求が約 4 倍になった）。

- 列の長さに上限を置き、超えたら **古い方から捨てる**。捨てたことは「実行環境の限界を超えた」としてログに残す（Kernel の失敗と同じ扱い。認知の出来事ではない）
- 上限の値は Environment の設定（Engineering）
- **あふれは、実行環境が足りないという計測結果として扱う。** あふれを減らすために、認知の側に機構を足さない（4 つの問いの 4）

### 3.4 意図の中身は、いつの受容野から作るか

| 案 | 中身 |
|---|---|
| **A. 発火した Pulse の受容野**（今と同じ） | 「何を考えようとしたか」は発火のときに決まっている。実行が遅れても中身は変わらない。来歴は発火時のスナップショット |
| B. 実行される Pulse の受容野（L2-2 の作り直し） | 実行の遅れで中身が変わる。Worker の数が中身を左右し、§2.4 に反する |

**A を推す。** 遅れて返ってくる結果は「時間のかかった考え」として、これまでどおり受け取る。

### 3.5 Worker の数が変わっても変わらないべきもの（不変条件）

- **変わらない**：どの Unit が、いつ、何を材料に計算を使おうとしたか（意図の列）。ただし、計算の結果が下流に戻るタイミングが変わるので、**その後の** 発火は変わりうる
- **変わる**：計算が終わるまでの遅れ、結果が戻るタイミング、あふれの有無
- つまり Worker の数は「思考の速さ」を変えるが、「考えようとしたこと」の発生条件は変えない。これを実装のテストで確かめる（同じ入力・同じ個体で、容量 1 と容量 4 の実行の、最初の結果が戻るまでの意図の列が一致すること）

## 4. この仕様で扱わないこと

- **認知的な競合（注意など）**：多数の表象の中から一部だけが処理に上がる、という仕組みを入れるなら、それは実行資源とは独立に、脳の設計図の側に明示的に作る。Worker の数とは独立でなければならない。今回は作らない
- 不応期（監査 §3.2）：もともと「同じ Unit が計算資源を連続で占有しない」ためだった。この仕様で実行の順番と並べ方を決めれば、その役目は実行基盤から外れる。不応期そのものの扱いは次の監査項目として別に決める
- Delta の保持期間・最新 8 件（監査 §3.4・3.5）：時間と記憶の設計と一緒に

## 5. 今の実装とのずれ

| 今の実装 | 仕様案 | ずれの扱い |
|---|---|---|
| 容量の取り合いに負けた要求は消える | 列に並ぶ（§2.3 の 1、§3.1） | 実装の変更が必要 |
| 計算中の Unit の新しい要求は消える | 列に並ぶ（§3.2） | 実装の変更が必要 |
| 実行の順番は claim の強さ（同点は回す） | 到着順（同じ Pulse は回す）（§3.1） | 実装の変更が必要 |
| 下書きは発火した Pulse の受容野から | 同じ（§3.4） | ずれなし |
| 発火の結果（activity・順応）は実行と無関係 | 同じ（§2.1） | ずれなし |
| 列の上限・あふれの扱いはない | 上限と「実行環境の限界」の記録（§3.3） | 実装の追加が必要 |

## 6. 予想される影響（先に書いておく）

- 実装を変えると、`minimal-v1` の上での振る舞いは変わる。0006 と同じく、これまで消えていた u1・u2 の計算が実行され、u1 ↔ u2 の相互結合が働いて活動が増える見込みが高い
- **それは、この仕様の副作用ではなく、動作テスト用の配線と、文章をやり取りする内部表現（監査 §3.6・3.8）の性質**として記録する。活動の増加を打ち消す機構は足さない
- これまでの実験（0002〜0005）は「要求が消える実行基盤」の上で得たものとして、前提つきで読む。変更後に基準をとり直すかどうかは、実装のときに事前登録で決める

## 7. 決めてほしいこと

1. 各層の責務（§2）でよいか
2. 実行の順番を到着順にし、claim の強さを使わない（§3.1 A）でよいか
3. 計算中の Unit の新しい意図も並べる（§3.2 A）でよいか
4. 列の上限とあふれの扱い（§3.3）でよいか
5. 意図の中身は発火した Pulse の受容野から（§3.4 A、今と同じ）でよいか
6. 不変条件（§3.5）の定義でよいか
