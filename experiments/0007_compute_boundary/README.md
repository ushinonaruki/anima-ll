# 0007 計算資源境界の実装確認と、基準の取り直し

> 種別：**検証（事前登録）＋ 記録**。このファイルは実装の前にコミットする。`run.py`・`analyze.py` は実装後、**測定を始める前に** コミットする（このファイルの判定基準は変えない）
> 登録日：2026-10-07（案）
> 仕様：`docs/compute-boundary-spec.md` v0.3.1
> 構成：脳 `minimal-v1`、偽 Kernel（`fake_delayed`）、時計の早送り（1 Pulse = 1 秒）。LLM は使わない

## 背景

計算資源境界の仕様（v0.3.1）を実装すると、実行基盤は意図を黙って捨てなくなる。これまでの実験（0002〜0005）は「容量不足・計算中なら要求が消える」実行基盤の上で得たものなので、その前提が変わる。

この実験の目的は 2 つ。

1. **パート A（主・合否）**：仕様の境界が、実装で本当に成り立っているかを確かめる
2. **パート B（記録・判定なし）**：新しい実行基盤の上で、`minimal-v1` がどう振る舞うかを基準として取り直す

**活動が増えるか減るかは評価しない。** 増えても減っても、それを打ち消す・補う機構は足さない（恣意性監査 §2.2・仕様 §8）。

## パート A：境界が成り立っているか（主）

### A の条件

| 名前 | Kernel の遅延 | Worker の数 | 長さ | 個体 |
|---|---|---|---|---|
| A-通常 | 3 秒（0004 と同じ） | 1・4 | 3600 Pulse、入力なし | seed 1〜20 |
| A-停止 | 事実上返らない（10⁹ 秒） | 1・4 | 300 Pulse、入力なし | seed 1〜20 |

- 列の上限：計算資源の種類ごとに 256（Engineering、仮置き）。あふれた run は劣化として扱う（仕様 §3.3）

### A の判定項目

| 項目 | 内容 | 対象 |
|---|---|---|
| **A1 消えない** | 作られた意図はすべて、`intent_completed`・`intent_kernel_error`・`intent_rejected_overflow` のどれかで終わるか、run の終了時点で「実行中」「待ち」として残っている。それ以外の消え方が 0 件。旧来の `rejected`（容量負け）・busy による捨て が 0 件 | A-通常・A-停止 |
| **A2 台数で変わらない** | A-停止で、同じ seed の Worker 1 と 4 の、意図の列（intent_id・unit_id・created_pulse・input_delta_ids・下書きのハッシュ）が完全に一致する（どちらもまだ結果が 1 件も返っていないため） | A-停止 |
| **A3 Unit ごとの順序** | どの Unit でも、実行の開始順 ＝ intent_seq 順。同じ Unit の同時実行は最大 1 件。結果を受け取る順 ＝ 意図を出した順 | A-通常・A-停止 |
| **A4 Worker を遊ばせない** | どの Pulse でも、取り出しの直後に「空いた Worker があり、かつ実行できる意図が待っている」状態が 0 回 | A-通常・A-停止 |

**判定**：A1〜A4 が **全 run で** 成り立てば「境界は実装された」。一つでも破れたら実装の誤りとして直し、パート A を最初からやり直す（やり直したことと理由をこのファイルに追記する）。パート B は A が通ってから行う。

A はソフトウェアの検証に近い。同じ内容を、契約テスト（仕様 §3.2：空き Worker 0・1・4 で同じ ComputeIntent が作られる）として `tests/` にも入れる。

## パート B：新しい基盤での基準の取り直し（記録）

### B の条件

| 名前 | 実行基盤 | 順応 | Worker | 備考 |
|---|---|---|---|---|
| B-new-v1 | 新 | `minimal-v1`（α = 0.01、τ_a = 300） | 1・4 | 新しい基準 |
| B-new-α0 | 新 | α = 0 | 1・4 | 順応なしの対照 |
| B-old-v1 | 旧（main `3ae66e7`） | `minimal-v1` | 1 | 比較のため。0004 の該当条件の再現 |
| B-old-α0 | 旧 | α = 0 | 1 | 同上 |

- 入力なしで 3600 Pulse、Kernel の遅延 3 秒、seed 1〜20
- 列があふれた run は劣化として集計から外し、件数だけを記録する

### B で記録するもの（判定には使わない）

- 全 Unit の発火回数（序盤 1〜600 Pulse、終盤 1801〜3600 Pulse、10 分あたり）。Unit ごとの内訳
- 0004 の H1 の個体ごとの基準（「終盤 < 序盤」かつ「終盤 < 同じ個体の α = 0 の終盤」）を満たす個体の数
- 意図の数（10 分あたり）、完了・失敗・あふれの数
- 列の長さ（最大・平均・終了時）と、時間とともに伸び続けているか（終盤の 1 次の傾き）
- 意図ができてから実行が始まるまでの待ち時間（Pulse）の分布
- 発話の回数
- 各 Unit の計算が実行された回数（u1・u2 が実行されるようになったか）

## 先に決めておくこと（結果を見る前に）

- 活動は増える見込みが高い（仕様 §8）。**増えても、抑える機構は足さない**
- **新しい基盤で 0004 の「落ち着く」（20 個体中 16 以上）が成り立たなくなった場合**：
  - 0004 の H1 の支持は「要求が消える旧基盤の上でのもの」と記録する
  - `minimal-v1` の順応のパラメータ（α = 0.01・τ_a = 300）は、恣意性監査で **要再検証** にする
  - **ここでパラメータを選び直さない。** 選び直すなら、別の実験として事前登録する
- 列が伸び続ける場合（意図の量に対して Kernel が遅すぎる）：性能不足の計測結果として記録する。意図を減らす仕組みを認知の側に足さない（仕様 §3.3）
- 結果を見たあとの分析は「事後の探索的観察」として分けて書き、上の判定は変えない

## 決めたいこと（レビューで）

1. 旧基盤との比較（B-old）を入れるか。0004 の再現にはなるが、新しい情報は少ないかもしれない
2. Kernel の遅延を 3 秒だけにするか。遅延を変えた条件（例：10 秒）も記録に足すか
3. 列の上限 256 は「あふれない程度に大きい値」として置いた仮の値でよいか
