# 0007 計算資源境界の実装確認

> 種別：**検証（事前登録）**。このファイルは実装の前にコミットする。`run.py`・`analyze.py` は実装後、**測定を始める前に** コミットする（このファイルの判定基準は変えない）
> 登録日：2026-10-07（案 v0.2）
> 仕様：`docs/compute-boundary-spec.md` v0.3.1
> 構成：脳 `minimal-v1`、偽 Kernel（`fake_delayed`）、時計の早送り（1 Pulse = 1 秒）。LLM は使わない
>
> v0.2（ChatGPT レビュー反映）：主な検証を「silent drop の除去」「意図の不変性」「Unit の力学を変えていないこと」の 3 点にした。新しい基盤の上での基準の取り直しはこの実験から外し、通ったあとで別に判断する。比較条件を 旧 main ／新 Worker 1 ／新 Worker 4 の 3 つにした

## 目的

計算資源境界の仕様（v0.3.1）で決めた **認知と実行基盤の境界が、実装で本当に切れたか** を確かめる。

この実験は「挙動が良くなったら成功」ではない。発火・計算・発話の量や Unit ごとの比率は **正式な判定に入れない**。増えても減っても失敗ではなく、それを抑える・補う機構にも進まない（恣意性監査 §2.2・仕様 §8）。

## 実装の範囲（先に決めておくこと）

- 変えるのは Runtime（実行基盤）と Environment の設定（列の上限）だけ
- **Neuroarchitecture に新しい状態変数を足さない。** activity・threshold・adaptation・発火の式は変えない
- 0006 の持ち越し（pending）とは別物である。持ち越しの圧力・減衰・再試行・統合（MERGED）のような Unit の状態は一切ない。発火 → ComputeIntent の成立 → Runtime の列、で終わる

## 条件

| 名前 | 実行基盤 | Worker | 役割 |
|---|---|---|---|
| **OLD** | 旧（main `3ae66e7`、容量・busy で捨てる） | 1 | 旧基盤がどれだけ認知の出来事を消していたかを測る（比較のため。改善を見るためではない） |
| **NEW-1** | 新 | 1 | 本命 |
| **NEW-4** | 新 | 4 | 本命（NEW-1 との比較が境界のテスト） |

各条件で次の 2 種類を回す。

| 種類 | Kernel の遅延 | 長さ | 個体 |
|---|---|---|---|
| **通常** | 3 秒（0004 と同じ） | 3600 Pulse、入力なし | seed 1〜20 |
| **停止** | 事実上返らない（10⁹ 秒） | 300 Pulse、入力なし | seed 1〜20 |

- 列の上限：計算資源の種類ごとに 256（Engineering、仮置き）。あふれた run は劣化として扱い、件数を記録する（仕様 §3.3）

## 正式な判定（pass／fail）

### P1 silent drop がなくなった

- NEW-1・NEW-4 の全 run で、作られた意図はすべて `intent_completed`・`intent_kernel_error`・`intent_rejected_overflow` のどれかで終わるか、run の終了時点で「実行中」「待ち」として残っている
- それ以外の消え方が 0 件。旧来の容量負け（`rejected`）と、busy による捨てが 0 件
- 計算中の Unit が新しく出した意図も、消えずに列に入っている
- あふれ（`intent_rejected_overflow`）は、消えたのではなく明示的な異常として別に数える

### P2 実行資源が意図そのものを変えない

- 「停止」で、同じ seed の NEW-1 と NEW-4 の意図の列が完全に一致する。比べる項目は、意図を出した Unit・created_pulse・input_delta_ids・origin_snapshot_id・下書きのハッシュ
- どちらもまだ結果が 1 件も Unit に返っていない区間なので、Worker の数だけが違う

### P3 Unit の力学を変えていない

- **コード**：`src/anima_ll/unit/` の力学（`simple_activity_dynamics.py`・`activity_dynamics.py`）に、main `3ae66e7` からの差分がない。`ActivityState` の項目が増えていない。脳の設計図のスキーマに新しい項目がない
- **依存**：Unit の層が、実行の列・Worker・Scheduler を参照しない（今ある AST の依存テストに、この条件を足す）
- **振る舞い**：「停止」では、どの条件でも結果が 1 件も返らないので、Unit が受け取る入力は OLD・NEW-1・NEW-4 で同じになる。このとき、同じ seed の **全 Unit の状態の推移（activity・adaptation・発火した Pulse）が 3 条件で完全に一致する**。旧基盤が意図を捨てていても、新基盤が並べていても、Unit の状態遷移は列の都合を参照していないことの確認

**判定**：P1〜P3 がすべての run で成り立てば「境界は実装された」。一つでも破れたら実装の誤りとして直し、最初からやり直す（やり直したことと理由をこのファイルに追記する）。

### 前提として確認すること（実装の正しさ。テストにも入れる）

- 同じ Unit の実行は同時に最大 1 件で、開始順 ＝ intent_seq 順。結果を受け取る順 ＝ 意図を出した順
- 取り出しの直後に「空いた Worker があり、かつ実行できる意図が待っている」状態が 0 回（work-conserving）
- 契約テスト（仕様 §3.2）：同じ Unit の出力を Runtime に渡すと、空き Worker が 0・1・4 のどれでも同じ ComputeIntent が作られる

これらが破れた場合も実装の誤りとして直す。

## 記録するもの（判定には使わない）

「通常」の run で、次を記録する。

- **OLD がどれだけ消していたか**：OLD で作られた計算の要求のうち、容量負け・busy で捨てられた数と割合（Unit ごと）
- NEW-1・NEW-4 の意図の数、完了・失敗・あふれの数
- 列の長さ（最大・平均・終了時）と、伸び続けているか
- 意図ができてから実行が始まるまでの待ち時間（Pulse）
- 発火・計算・発話の回数と Unit ごとの内訳（OLD・NEW-1・NEW-4）

これらは「silent drop という工学的なブレーキを外した結果、この動作テスト用の配線ではこうなった」という観察としてだけ書く。**新しい基準（周期性・落ち着き方・発話の頻度など）としては採用しない。**

## この実験のあとで

- P1〜P3 が通ったら、新しい基盤の上で `minimal-v1` の基準（0004 の「落ち着く」など）を取り直す必要があるかを、記録を見て **別に判断する**。取り直すなら、別の実験として事前登録する
- 0004 の H1 の支持は、それまで「要求が消える旧基盤の上でのもの」として前提つきで読む
- 列が伸び続ける場合（意図の量に対して Kernel が遅すぎる）は、性能不足の計測結果として記録する。意図を減らす仕組みを認知の側に足さない（仕様 §3.3）
- 結果を見たあとの分析は「事後の探索的観察」として分けて書き、上の判定は変えない
