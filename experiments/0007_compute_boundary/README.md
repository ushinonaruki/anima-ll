## 目的

計算資源境界の仕様（v0.3.1）で決めた **認知と実行基盤の境界が、実装で本当に切れたか** だけを確かめる。

この実験は工学の検証であり、認知の評価ではない。発火・計算・発話の量や Unit ごとの比率は扱わない。それらは、この実験が通ったあとの別の実験（§「この実験のあとで」）で扱う。

## 実装の範囲（先に決めておくこと）

- 変えるのは Runtime（実行基盤）と Environment の設定（列の上限）だけ
- **Neuroarchitecture に新しい状態変数を足さない。** 0006 の持ち越し（pending）とは別物で、持ち越しの圧力・減衰・再試行・統合（MERGED）のような Unit の状態は一切ない。発火 → ComputeIntent の成立 → Runtime の列、で終わる
- 列と意図の一生（作成・受理・開始・完了など）の状態は Runtime にだけ置く

## 正式な判定（pass／fail）

A0〜A5 のすべてが成り立てば「境界は実装された」。一つでも破れたら実装の誤りとして直し、最初からやり直す（やり直したことと理由をこのファイルに追記する）。

### A0 Unit の力学（Neuroarchitecture）を変えていない

**コード・設定**

- `ActivityState` に新しい項目を足していない
- `SimpleActivityDynamics` の式（減衰・刺激・内在的駆動・閾値・不応期・順応・発火）を変えていない。`src/anima_ll/unit/dynamics/` に main `3ae66e7` からの差分がない
- `config/neuroarchitecture/minimal-v1.yaml` を変えていない。脳の設計図のスキーマに新しい項目がない
- 「実行資源の都合を表す Unit の状態」（pending のようなもの）がない
- Unit の層が、実行の列・Worker・Scheduler・意図の一生の状態を参照しない（今ある AST の依存テストに、この条件を足す）

**振る舞い**

- Kernel が結果を返さない設定（遅延 10⁹ 秒）で 300 Pulse、入力なし、seed 1〜20 を、旧基盤（main `3ae66e7`）・新基盤 Worker 1・新基盤 Worker 4 で回す
- 結果が 1 件も返らないので、Unit が受け取る入力（u0 の内在的駆動による発火と、その中継だけ）は 3 つで同じになる
- **同じ seed の全 Unit の状態の推移（activity・adaptation・発火した Pulse）が 3 つで完全に一致すること**。旧基盤が意図を捨てていても、新基盤が並べていても、Unit の状態遷移は列の都合を参照していないことの確認

### A1 silent drop がない

シナリオ（テストとして書く）：

- 容量が埋まっている（Worker 1 が実行中）ときに、別の Unit が意図を出す → 列に入り、消えない
- 同じ Unit が実行中に、新しい意図を出す → 列に入り、消えない
- どちらも、のちに Worker が空いたら実行され、`intent_completed` で終わる
- 旧来の容量負け（`rejected`）・busy による捨てのログが出ない

### A2 Worker の数で、成立済みの意図が変わらない

- 契約テスト（仕様 §3.2）：同じ Unit の出力を Runtime に渡すと、空き Worker が 0・1・4 のどれでも同じ ComputeIntent（intent_id・unit_id・created_pulse・input_delta_ids・origin_snapshot_id・下書き）が作られる。違うのは開始・完了の時刻だけ
- 結合：A0 の「結果を返さない」run で、同じ seed の新基盤 Worker 1 と 4 の意図の列（上の項目と下書きのハッシュ）が完全に一致する

### A3 Unit ごとの FIFO と 1 in-flight

シナリオ：

- Worker 4、同じ Unit の意図 A・B・C が列にある → 同時に実行されるのは 1 件だけ。開始順 ＝ A・B・C（intent_seq 順）
- A の計算が B より遅くても、結果が Unit に届く順は A・B・C

### A4 Worker を遊ばせない（work-conserving dispatch）

シナリオ：

- Worker 2、`u1:A` 実行中、列に `u1:B`・`u2:C` の順 → `u1:B` は飛ばして列に残し、`u2:C` を開始する。`u1:B` の順番は保たれ、A の完了後に開始する

### A5 あふれは明示的な劣化

シナリオ：

- 列の上限 2 の専用環境で、3 件目の意図を出す → `intent_created` のあと `intent_rejected_overflow` が記録される。すでに受理した 2 件は捨てられない。その run は劣化（degraded）として印がつく
- `intent_rejected_overflow` と `intent_kernel_error` は別の状態として記録される

## 列の上限（A5 以外）

A0〜A4 では、**あふれが正常系に混ざらない値を、構造上の最大値から導く**。

- `minimal-v1` で Kernel の計算を要求する Unit は u1・u2・u3 の 3 つ。「1 Unit 1 Pulse 1 件」の契約があるので、N Pulse の run で生まれうる意図は最大 3 × N 件
- 列の上限はこれより大きくする（300 Pulse なら 901 以上。実装で上限なしにできるならそれでもよい）
- 「256 なら足りるだろう」のような値は使わない
- この値は **0007 の正常系の検証にあふれを混ぜないための検証用の設定** であり、実運用で推奨する値ではない
- 構造上あふれないはずなので、A0〜A4 の run であふれが起きたら、それは FAIL ではなく **検証条件を満たしていない run（invalid）** として扱い、原因（上限の導き方の誤り・1 Pulse 1 件の契約違反など）を直してやり直す。あふれを含んだ run を「消えていないから A1 は通った」とは数えない

## 結合の動作確認（smoke。正式な判定ではない）

新基盤 Worker 1・4、Kernel の遅延 3 秒、入力なしで 3600 Pulse、seed 1〜20 を回し、例外や不整合（意図の一生の状態が途中で途切れる・同じ意図が 2 回実行される など）が出ないことを確認する。列の上限は 3 × 3600 ＋ 1 ＝ 10801 以上。

ここで不整合が出たら実装の誤りとして直すが、発火や計算の量は見ない・書かない。

## この実験のあとで（別の実験として事前登録する）

A0〜A5 が通ったら、新しい実行基盤を正しい足場として採用し、その上で次を **別の実験（0008 の予定）** として事前登録する。

- 新基盤での `minimal-v1` の baseline の取り直し（順応あり・なし）
- 旧基盤との比較：silent drop という偶然の抑制を外したことで、振る舞いがどれだけ変わったか（新方式が優れているかの比較ではなく、工学の層を変えた差分の記録）
- 0004 の「落ち着く」が新基盤でも成り立つか、順応のパラメータを再検証するか
- 活動量・発話量・列の長さ・待ち時間の観察
- Kernel の速さへの感度（遅延 10 秒など）は、必要になったらそこで扱う

それまで、0004 の H1 の支持は「要求が消える旧基盤の上でのもの」として前提つきで読む。

### 測定のあとで直したこと（判定基準は変えていない）

- `analyze.py` が、意図が 1 件も生まれない run（seed 9：入力なしでは、どの Unit も一度も発火しない個体）で例外を出して止まった。意図の一生の集計が「意図がある」前提になっていたため
- 修正：意図が 0 件の run は、消えうる意図がないので A1・A3 は自明に成り立つものとして扱い、件数を別に報告する（`runs_without_any_intent`）。A2 は事前登録どおり「seed ごとの完全一致」で判定し（空どうしも一致）、全体として比べる意図があること（442 件）も確かめる。修正前の script は A2 に「各 seed で意図が 1 件以上」という、事前登録にない条件を足していたので、それを外した
- 修正後の script は、このコミットに含める
