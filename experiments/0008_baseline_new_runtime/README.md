# 0008 新しい実行基盤の上での baseline の取り直し

> 種別：**検証（事前登録）＋ 記録**。このファイルは測定の前にコミットする。`run.py`・`analyze.py` も測定の前にコミットする（このファイルの判定基準は変えない）
> 登録日：2026-10-07（案 v0.2）
>
> v0.2（ChatGPT レビュー反映）：参照値を保つ条件を「H1-new 支持 **かつ** 0005 の NEW での再現」にした（0005 も参照値を選んだ根拠だったため）
> 前の実験：0007（計算資源境界の実装確認。A0〜A5 すべて成立）
> 構成：0004 のパート A と同じ（脳 `minimal-v0` ＋ 順応のパラメータ、偽 Kernel 遅延 3 秒、Worker 1、時計の早送り、入力なし 3600 Pulse）。実行基盤だけが違う

## 背景と目的

0007 で、実行基盤は意図を黙って捨てなくなった（main `7db0b66`）。これまでの実験 0002〜0005 は「容量不足・計算中なら要求が消える」旧基盤（main `3ae66e7`）の上で得たもので、0006 では、その捨てる仕組みが **偶然ネットワークの強い抑制として働いていた** ことが分かっている。

この実験の目的は 2 つ。

1. **判定**：L2-1 で `minimal-v1` に入れた順応の根拠である 0004 の H1（入力がないと落ち着く）が、新しい基盤の上でも成り立つかを、0004 と **同じ判定基準で** 確かめる
2. **記録**：silent drop という工学的なブレーキを外したことで、振る舞いがどれだけ変わったかを記録する。これは「新しい方式が優れているか」の比較ではなく、工学の層を変えた差分の記録である

**活動量の増減は評価しない。** 増えても減っても、それを抑える・補う機構は足さない（恣意性監査 §2.2、計算資源境界 仕様 §8）。

## 条件

| 名前 | 実行基盤 | 脳と順応 | 個体 |
|---|---|---|---|
| **NEW** | 新（main `7db0b66`） | `minimal-v0` ＋ 0004 と同じ 10 条件（α = 0、α ∈ {0.005, 0.01, 0.02} × τ_a ∈ {30, 300, 1200}） | seed 1〜20 |
| **OLD** | 旧（main `3ae66e7`） | 同上 | seed 1〜20 |

- 入力なしで 3600 Pulse、偽 Kernel の遅延 3 秒、Worker 1（0004 と同じ）
- 列の上限：なし（0007 と同じ。3600 Pulse で生まれうる意図は最大 3 × 3600 件）
- `minimal-v1`（α = 0.01、τ_a = 300）はこの 10 条件の 1 つに当たる
- OLD は、0004 の結果をそのまま再現できているかの確認と、旧基盤との差分の記録に使う

## 判定（事前登録）

### 前提の確認：OLD が 0004 を再現する

OLD の 10 条件 × 20 個体の発火の記録が、0004 の `results.json.gz` のパート A と一致すること（Unit ごとの発火した Pulse が完全一致）。一致しなければ、測定の手順が 0004 と違っているので、原因を直してやり直す（判定には進まない）。

### H1-new：新しい基盤の上でも、入力がないと落ち着く

0004 の H1 と **同じ基準** を NEW に当てはめる。

- 指標：全 Unit（u0〜u3）の発火回数の合計。序盤（1〜600 Pulse）と終盤（1801〜3600 Pulse）で、10 分あたりに直す
- 個体ごとの判定：「終盤 < 序盤」かつ「終盤 < 同じ個体の α = 0 の終盤（NEW の α = 0）」
- 条件ごとの判定：20 個体中 16 個体以上で成り立てば、その条件で「落ち着く」
- **H1-new は、α ∈ {0.01, 0.02} × τ_a ∈ {300, 1200} の 4 条件すべてで「落ち着く」なら支持**

### 結果の扱い（先に決めておく）

`minimal-v1` の参照値（α = 0.01・τ_a = 300）は、0004 の H1 と 0005 の H2' の両方を根拠に、事前登録した規則で選んだ。そのため、参照値が新しい基盤の上でも根拠を保つのは、次の **両方** が成り立つときだけとする。

1. H1-new が支持される
2. 0005 の手順を NEW で回した結果が、0005 の結果を再現する（下の「0005 の再現」）

- **両方成り立つ** → 順応の機構と `minimal-v1` の参照値は、新しい基盤の上でも根拠を保つ。恣意性監査の L2-1 の行はそのまま
- **どちらかが成り立たない** → 参照値を、恣意性監査で **要再検証** にする。ここで選び直さない（下と同じ）
- **H1-new が不支持** →
  - 0004 の H1 の支持は「要求が消える旧基盤の上でのもの」だったと記録する
  - `minimal-v1` の順応の参照値を、恣意性監査で **要再検証** にする
  - **ここでパラメータを選び直さない。** 選び直すなら、別の実験として事前登録する
  - どの条件で、どちらの比較（序盤との比較／α = 0 との比較）が崩れたかを分けて記録する
- いずれの場合も、順応の機構そのもの（発火の履歴で実効閾値が上がる）の採否はここでは決めない。機構の根拠は 0004・0005 の両方にあり、0005（発火に必要な最小の入力）は次のとおり実行基盤に依存しない

### 0005 の再現（参照値を保つ条件の 2 つ目）

0005 の主指標は u0 の発火だけで決まり、u0 に届くのは受容器からの入力だけである（`minimal-v0` の配線で、Kernel の結果が u0 に戻る経路はない）。したがって 0005 の結果は実行基盤の変更で変わらないはずである。

- 0005 の手順（4000 本）を NEW で回し、**全組の w\* が 0005 の `results.json.gz` と完全に一致** すれば「再現」
- 一致しなければ「再現しない」とし、0005 の H2' の支持も「旧基盤の上でのもの」として前提つきで読み直す。参照値は上のとおり要再検証にする

## 記録するもの（判定には使わない）

条件ごと（NEW・OLD × 10 条件）に、個体ごとに記録する。

- Unit ごとの発火回数（序盤・終盤、10 分あたり）
- 意図（OLD では計算の要求）の数、完了の数。OLD では、容量負け・busy で捨てられた数と割合（Unit ごと）
- NEW の列の長さ（最大・平均・終了時）と、終盤に伸び続けているか（終盤の 1 次の傾き）
- NEW の待ち時間（意図ができてから実行が始まるまでの Pulse）の分布
- 発話（effector への出力）の回数
- 各 Unit の計算が実行された回数（u1・u2 がどれだけ実行されるようになったか）
- 終盤の周期パターンと変動係数（0004 と同じ定義）

これらは「silent drop という工学的なブレーキを外した結果、この動作テスト用の配線（恣意性監査 §3.8）と、文章をやり取りする内部表現（§3.6）の上ではこうなった」という観察としてだけ書く。**AnIma-ll の認知特性・性格とは解釈しない。**

## 予測（参考）

- NEW では、これまで消えていた u1・u2 の計算が実行され、u1 ↔ u2 の相互結合が働いて、発火・計算・発話が OLD より増える見込みが高い（0006 と同じ方向）
- 列が伸び続けるかどうかは分からない。伸び続けるなら、Kernel（遅延 3 秒・Worker 1）が意図の量に対して遅すぎる、という性能不足の計測結果として記録する。意図を減らす仕組みを認知の側に足さない（仕様 §3.3）
- H1-new は、相互結合による活動の持続が順応を上回れば不支持になりうる

## 恣意性監査との関係

この baseline は、今の不応期（3 Pulse）・内在的駆動（0.08）・Delta の保持期間（10 Pulse）などの上で取る。

- **不応期**：§3.2 で監査済み。独立した根拠がなく、除去する方向。ただし 0008 が終わるまでは baseline を固定するため、3 Pulse のまま測る。0008 のあとに除去の実験を事前登録する（結果で採否を選ばない）
- **内在的駆動・Delta の保持期間など**：引き続き要監査
- 監査の結果これらを変えた場合、その時点の baseline を取り直す。この実験の結果は、それまでの比較の基準として使う
- 次の監査項目は **§3.3 内在的駆動**
