## 1. この実験が決めること・決めないこと

(c2) は、Unit を動かす経路そのものを変える（Delta は駆動しない、発火が接続の重みで相手を駆動する、Kernel の結果は駆動しない）。この実験は、その上で **可塑性を入れる前の基準（baseline）** を測り、旧 minimal の結果（0009・0010 の駆動 0.0800）と並べて記録する。

**決めないこと**

- **値を調整しない**。(c2) のあとで活動が増えても減っても、内在的駆動・閾値・重み・順応の値を変えない。旧の結果に近づける調整もしない
- **(c2) を採るかどうかは決めない**。(c2) は境界の仕様（#39）で、症状ではなく原理（学ぶものと、学んだ重みが効くものを一致させる）から選んだ。この実験の結果で取り消さない
- 結果は、可塑性の実験（0012）の前提となる **新しい基準の記録** として使う

## 2. 設計図：`minimal-v3`

- 値は `minimal-v2` と **まったく同じ**（配線・重み・内在的駆動 0.08・閾値 0.5・減衰 0.85・jitter 0.1・順応 α 0.01／τ_a 300・不応期 0・max_inputs 8）
- 違いは、(c2) の駆動の経路で解釈されること。コメントにそう書く
- **旧の経路（Delta が駆動する）への切り替えは残さない**。旧の経路は、本設計として採らないと決めた形（監査 §4.4 の (a)）であり、切り替えを残すと実質的なモードの分岐になる。旧の結果は、データ（0009・0010 の保存済みの `json.gz`）と、その測定の commit で再現できる
- `minimal-v0`・`v1`・`v2` の設計図のファイルは書き換えない。ただし、(c2) の実装のあとのコードで動かすと、旧の結果とは違う振る舞いになる。それぞれのコメントに「旧の経路での結果は、測定の commit で再現する」と書き足す

### 3.1 B1・B2 の位置づけ

B1・B2 は仮説というより、**実装が仕様のとおりかの確認** に近い。

- B1：(c2) では Kernel の結果は駆動しない。Kernel が **いつ** 終わっても（待ち時間）、**何を** 返しても（中身あり・空）、**失敗** しても、発火の記録は 1 つも変わらないはずである。一致しなければ、仕様（C4）に反する経路が残っている

  | Kernel の条件 | 結果 | 遅延 |
  |---|---|---|
  | K-a | 成功・中身あり | 0 秒 |
  | K-b | 成功・中身あり | 3 秒 |
  | K-c | 成功・中身あり | 30 秒 |
  | K-d | 成功・中身あり | 3 秒 ± 3 秒のばらつき |
  | K-e | 成功・中身が空 | 3 秒 |
  | K-f | 失敗（中身なし） | 3 秒 |

  - 偽 Kernel には、結果の種類（中身あり・空・失敗）を指定する設定を、実装のときに足す（実験の道具であり、脳の設計図には入れない）
  - 中身・空・失敗で変わってよいのは、中身の Delta（受容野・発話の記録）と運用のログだけ。発火の記録は変わらない
- B2：u0 に入るのは Receptor からの感覚の駆動だけで、旧の経路でも「1 つの入力 × 重み」だった。(c2) でも「1 つの SensoryEvent × 重み」なので、u0 の振る舞いは変わらないはずである。一致しなければ、感覚の駆動の強さか時刻が旧と違っている
- **B1・B2 が成り立たないときは、実装を仕様に合わせて直す**（値を調整するのではない）。直したあとは、run.py・analyze.py・判定基準を変えずに測り直し、何を直したかを結果に記録する

### 3.2 B3・B4 の位置づけ

B3・B4 は、旧の知見（K1・K2）が新しい経路の上でも成り立つかの **再確認** である。

- 成り立たなくても、値を変えない・仕組みを足さない。旧の知見の適用範囲として「旧の経路（Delta が駆動する）の上でだけ成り立つ」と恣意性監査と L2-1 の行に書く
- B4 は u0 での測定なので、B2 が成り立てば、旧と同じ結果になる（B4 は B2 から決まる）。それでも、判定は独立に行い記録する
- 順応の参照値（α 0.01・τ_a 300）の選び方の規則（旧 K3）は、B3・B4 がともに成り立ったときだけ当てはめ、選ばれた条件を記録する。**参照値は変えない**

## 4. 予測（参考。判定には使わない）

- **入力なしの発火は大きく増える**と予測する。旧の経路では、u0 が内在的駆動だけで発火しても relay は何も送らず、u1・u2 は動かなかった。(c2) では u0 の発火のたびに u1・u2 へ重み 1.0 の駆動が届き、閾値 0.5 を越えるので、u1・u2 はほぼ毎回すぐ発火する。u1 ↔ u2（0.4）、u1 → u3（0.6）の駆動も加わる
- その結果、u1・u2・u3 の kernel_request が増え、Worker 1・遅延 3 秒では計算の列が伸び続ける可能性が高い（Kernel の性能の問題として記録する。B1 のとおり、列が伸びても発火は変わらない）
- B3 は、順応が u1・u2 にも強く効くので「落ち着く」側に出る可能性もあるが、自信はない

## 5. 記録するもの（判定には使わない）

B3 の実行で、条件ごと・Unit ごとに：

- 発火の数（序盤 1〜600・終盤 1801〜3600、10 分あたり）。**旧の経路（0010 の駆動 0.0800）の同じ seed・同じ条件と並べる**
- Unit ごとの発火の時刻の関係：u0 の発火の次の Pulse に u1・u2 が発火した割合
- 周期のパターンと変動係数（0004 と同じ定義）
- 意図の数・完了の数、列の長さ（最大・平均・終了時）と伸び続けたか、待ち時間
- 発話（Effector に届いた中身）の数
- 一度も発火しない個体の数

これらは動作テスト用の配線（恣意性監査 §3.8）の上の観察であり、AnIma-ll の認知特性とは解釈しない。

## 6. 実行の手順（予定）

1. この README と `protocol.yaml` をコミットする（実装の前）
2. (c2) を実装し、契約テスト（境界の仕様 §9 の T1〜T8）を通す
3. `run.py`・`analyze.py` を書く。protocol.yaml を読み、条件・基準の数字をスクリプトに直接書かない。0004・0005 の手順の関数を再利用し、判定の値は protocol.yaml からだけ取る。`--seeds 1`（結果は使わない）で動作を確かめてから、測定の前にコミットする
4. 測定し、`report.json` に測定の commit を残す
5. 結果を見たあとの分析は「事後の探索的観察」として分け、上の判定は変えない
